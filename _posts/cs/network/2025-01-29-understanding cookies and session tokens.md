# 쿠키와 세션 토큰 이해하기
서버가 클라이언트의 인증을 확인하는 방식에는 쿠키, 세션, 토큰 등이 대표적으로 사용된다. 이들 기술이 필요한 이유를 먼저 살펴본 후, 각각의 개념과 특징에 대해 자세히 알아보자.

## 왜 인증이 필요한가?
서버가 인증을 요구하는 이유는 **보안, 자원 보호, 무단 접근 방지, 서비스 제공, 신뢰성**을 보장하기 위해서이다. 인증을 통해 서버는 클라이언트와의 상호작용을 안전하고 효율적으로 관리할 수 있다. 
1. **사용자 식별**
서버는 클라이언트를 식별하여 적절한 데이터와 서비스를 제공한다. 예를 들어, 사용자 A의 요청에는 사용자 A에 맞는 정보와 응답이 제공되어야 한다.
2. **무단 접근 방지**
인증을 통해 서버는 요청이 적법한 사용자나 시스템으로부터 온 것인지를 확인할 수 있다. 이를 통해 자원 탈취나 악의적 공격으로 인한 데이터 손상 또는 유출을 방지한다.
3. **상태 유지/추적**
인증된 클라이언트는 로그인 상태를 유지하거나, 비로그인 상태에서도 장바구니 정보나 아이디 기억 등의 편의 기능을 제공받을 수 있다. 또한, 클라이언트의 상태를 추적하여 지속적인 서비스를 제공할 수 있다.

## Cookies
쿠키는 브라우저에 저장되는 Key-Value 형식의 데이터로, 인증 방식 중 하나로 사용된다. 각 클라이언트마다 고유한 쿠키를 보유하고 있어 정보 식별과 상태 정보를 저장하는 데 유용하다. 그러나 쿠키에는 몇 가지 단점이 있다.  
* **보안 위험**: 쿠키가 유출되거나 조작될 위험이 존재한다.
* **용량 제한**: 쿠키의 크기에 제한이 있어 저장할 수 있는 정보량이 한정적이다.
* **호환성 문제**: 브라우저에 따라 호환되지 않는 쿠키 종류가 있을 수 있다.
* **네트워크 부하**: 쿠키 크기가 커지면 네트워크 부하가 증가할 수 있다.  

**CORS(Cross-Origin Resource Sharing)**  
웹 어플리케이션에서 세션을 관리할 때, 쿠키는 주로 단일 도메인이나 서브 도메인에서만 작동하도록 설계된다. 따라서 쿠키를 여러 도메인에서 관리하려면 추가적인 설정이나 번거로운 작업이 필요하다.

### 인증 방식
![Image](https://github.com/user-attachments/assets/7905ac3e-8f02-4c1f-a87e-f68ae135afea)  
[출처: Using HTTP cookies](https://developer.mozilla.org/en-US/docs/Web/HTTP/Cookies)  

1. 클라이언트는 서버에 요청을 보낸다.
2. 서버는 응답 헤더에 Set-Cookie 인증 정보를 담아 보낸다.
3. 이후 요청 때마다, 요청 헤더에 쿠키를 담아 클라이언트를 식별한다.

## Session
세션은 쿠키의 보안적 단점을 보완하기 위해, 인증 정보나 상태 데이터를 서버 측에 저장하고 관리하는 방식이다. 서버는 클라이언트의 상태를 추적하는 정보를 서버 메모리, 로컬 파일, 또는 데이터베이스에 저장하여 관리한다. 이 방식은 클라이언트 측에서 중요한 정보가 유출될 위험이 줄어들고, 보안성을 높일 수 있다.  

세션은 쿠키의 보안적 단점을 보완하기 위해 인증 정보나 상태 데이터를 서버 측에 저장하고 관리하는 방식이다. 서버는 클라이언트의 상태를 추적하는 정보를 서버 메모리, 로컬 파일, 또는 데이터베이스에 저장하여 관리한다. 이 방식은 클라이언트 측에서 중요한 정보가 유출될 위험을 줄이고, 보안성을 높일 수 있다.

세션은 클라이언트가 서버와 상호작용할 때마다 고유한 세션 ID를 쿠키로 클라이언트에 전달하고, 서버는 이를 사용하여 세션 데이터를 조회하고 상태를 유지한다. 세션 ID는 외부에 노출되더라도 민감한 데이터를 포함하지 않기 때문에 본래 안전하지만, 해커가 세션 ID를 탈취하거나 위장할 수 있는 위험이 존재한다. 만약 해커가 세션 ID를 확보하면, 인증된 사용자처럼 행동할 수 있다.

또한, 클라이언트의 요청 수가 많아짐에 따라 각 서버 간의 세션 정보 공유와 관리가 복잡해지고, 이로 인해 서버 확장성에 어려움이 발생할 수 있다. 여러 서버가 같은 세션 정보를 유지하고 관리해야 하므로, 세션을 관리하기 위한 추가적인 인프라가 필요하고, 확장성이 떨어질 수 있다.  

### 인증 방식
![Image](https://github.com/user-attachments/assets/f5dd8983-55f3-4715-8e2a-3955dcdd80da)  
[출처: [JWT] 토큰(Token) 기반 인증에 대한 소개](https://velopert.com/2350)  

1. 사용자 로그인 요청에 대한 Session을 서버에 저장 후, 식별 목적의 Session Id를 쿠키에 전달한다.
2. 이후 요청마다 클라이언트는 해당 서버에 Session Id를 쿠키에 담아 전송한다.
3. 서버는 받은 Session Id와 서버에 저장된 Session과 비교하여 인증을 수행한다.

## Tokens
서버는 클라이언트에게 암호화된 "토큰"이라는 유일한 인증 표식을 제공한다. 토큰은 쿠키 방식과 유사하게, 클라이언트가 요청 헤더에 담아 서버에서 제공한 토큰과 일치 여부를 확인한 후 인증을 처리하는 방식이다. 기존 세션 방식은 서버에서 세션을 저장하고 인증을 조회하는 과정에서 많은 오버헤드가 발생하지만, 토큰은 브라우저에 저장되므로 부하 문제를 보완할 수 있다. 또한, 서버는 상태를 유지하지 않기 때문에 Stateless(무상태) 특성을 가진다.  

하지만, 쿠키나 세션과 다르게, 토큰 자체의 데이터 길이가 길어지면 요청 시 인증 과정에서 오버헤드가 발생할 수 있다. 또한, Payload는 암호화되지 않기 때문에 민감한 정보를 포함해서는 안 된다. 예를 들어, JWT와 같은 토큰은 암호화되지 않은 상태로 데이터를 담고 있기 때문에, 토큰이 탈취되면 해당 정보가 유출될 위험이 있다. 따라서 민감한 정보는 항상 별도로 암호화하거나, 토큰 내에 포함시키지 않아야 한다.  

또한, 토큰의 유효성 기간을 단기로 설정할 수는 있지만, 토큰이 탈취당하면 대처하기 어려운 문제도 존재한다. 토큰이 탈취되면, 해당 토큰이 유효한 기간 동안 악의적인 사용자가 인증된 사용자처럼 행동할 수 있기 때문이다. 이를 방지하기 위해 토큰의 유효 기간을 짧게 설정하는 것도 하나의 방법이지만, 여전히 토큰이 탈취될 위험이 존재하므로, 리프레시 토큰(refresh token) 시스템이나 주기적인 세션 갱신 등 추가적인 보안 조치를 고려해야 한다.  

### 토큰 기반 인증 시스템의 구현체 
토큰은 인증 방식 중 대표적인 방식으로 **JWT (JSON Web Token)**가 있다. JWT는 JSON 형식으로 데이터를 안전하게 전달하기 위해 사용되며, 서버와 클라이언트 간의 인증 및 정보 전달에 주로 활용된다. JWT는 인증 정보를 포함하고 있어, 서버는 토큰을 검증함으로써 클라이언트의 인증 상태를 확인할 수 있다.

### 모바일 APP 
Android / iOS 모바일 어플리케이션을 개발 한다면, 토큰 기반 인증이 이상적인 선택이 될 수 있다. 

### 인증정보를 다른 어플리케이션으로 전달
페이스북/구글/네이버 같은 소셜 계정을 이용하여 다른 웹 서비스에서도 로그인할 수 있게 해주는 OAuth도 대표적인 토큰 기반 인증 시스템이다. OAuth는 사용자가 여러 서비스에 쉽게 로그인할 수 있도록 해주며, 인증 정보를 안전하게 다른 애플리케이션에 전달하는 데 유용하다.  

### 인증 방식
![Image](https://github.com/user-attachments/assets/f91bfa9e-ab7e-4716-9f01-b8c35feb82dc)  
[출처: [JWT] 토큰(Token) 기반 인증에 대한 소개](https://velopert.com/2350)  

1. 로그인을 할 경우, 서버 측에서 고유 토큰을 생성 후에 클라이언트에게 응답 값으로 전달한다.
2. 클라이언트는 토큰을 쿠키나 스토리지에 저장해 두고, 서버에 요청을 할 때마다 해당 토큰을 Http 요청 헤더에 포함시켜 전달한다.
3. 서버는 전달 받은 토큰을 검증한다. 토큰 내부에 데이터가 포함되어 있어, 따로 조회할 필요는 없다.
