# 소개
웹이 고품질 서비스를 안정적이고 빠르게 제공할 수 있는 이유는 캐시 기술 덕분이다.  

캐시는 임시 공간에 데이터를 보관 및 빠른 접근, 조회, 응답이 가능한 구조를 제공한다.  
왜 빠른 접근 및 조회가 가능할까? 그건 바로 캐시가 RAM보다 더 빠른 저장 공간으로, CPU와 RAM 사이에서 데이터를 중계하는 역할이기 때문이다.  
그래서 성능 최적화, 서버 부하 감소, 클라우드 비용 절감, 쾌적한 환경을 제공하여 사용자 경험 향상 등 지속적이고 일관된 안정적인 서버 운영이 가능하다. 

실제로 사용자가 웹 페이지에 접근하면 브라우저는 웹 페이지의 자원(이미지, css, js)을 캐싱하여, 재방문 시 로컬 캐시에서 불러들인다.  

캐싱은 웹 최적화 방법 중에 하나이다. 캐싱을 이해한다면, 시스템의 성능을 극대화하고, 비용을 절감하며, 안정적이고 확장 가능한 서비스를 설계할 수 있는 능력을 갖출 수 있는 기초를 다질 수 있다.  

# 캐싱(Caching)
캐싱은 사용자가 자주 사용할 데이터를 캐시 메모리나 디스크와 같은 임시 저장소에 저장하여, 데이터를 빠르게 가져올 수 있게 해 주는 프로세스이다. 임시 저장소에 저장된 데이터는 일정 시간이 지나면 갱신되거나 삭제되는, 즉 유효성 관리 시스템을 통해 처리된다.  

## 캐싱을 사용한다면
- **응답 속도 향상**
자주 사용하는 데이터를 메모리나 빠른 저장소에 저장하기 때문에, 반복적인 데이터 요청에 대해 빠르게 응답할 수 있다. 예를 들어, 웹사이트에서 자주 조회되는 상품 정보나 사용자 세션 정보를 캐시하면, 페이지 로딩 시간이 매우 빨라져 사용자 경험이 향상된다.  
- **서버 부하 감소**
자주 요청되는 데이터를 캐싱하면, 데이터베이스나 서버의 부하가 줄어든다. 이는 같은 데이터를 반복해서 계산하거나 쿼리하지 않기 때문에 시스템의 자원을 효율적으로 사용할 수 있다. 예를 들어, 인기 있는 상품 목록을 캐시하면, 데이터베이스에 대한 쿼리 요청이 줄어들어 데이터베이스의 부하가 감소한다.  
- **비용 절감**
캐시를 사용하면 네트워크 비용과 서버 자원을 절약할 수 있다. 반복적인 요청을 캐시에서 처리함으로써, 서버와 네트워크의 부담을 줄이고 더 적은 리소스로 많은 요청을 처리할 수 있기 때문에 비용 절감으로 이어진다. 클라우드 환경에서는 요청을 캐시로 처리함으로써, 데이터 전송 비용과 인프라 확장 비용을 절감한다.  
- **사용자 경험 향상**
캐시는 페이지 로딩 속도를 크게 개선하여, 사용자 경험을 향상시킨다. 빠른 응답 시간은 사용자가 서비스를 계속 사용하도록 유도하고, 이탈을 방지하는 데 중요한 역할을 한다.  
- **서비스 안정성 증가**
캐시는 고가용성을 높이고, 장애 조치를 지원한다. 원본 데이터베이스가 다운되더라도 캐시된 데이터를 이용해 서비스가 계속 제공될 수 있게 한다.  
- **높은 확장성 지원**
캐시 시스템은 여러 서버에 데이터를 분산 저장할 수 있어, 수평 확장(scale out)이 용이하다.  또한, 캐시 서버는 빠르게 추가하거나 제거할 수 있어, 트래픽 급증에 대응이 가능하다. 예를 들어, Redis와 같은 분산 캐시 시스템을 사용하면 트래픽이 증가해도 성능을 유지할 수 있다.  
- **다양한 캐싱 전략 활용 가능**
캐시는 다양한 전략을 적용할 수 있다. 시스템에 맞는 최적의 방법을 선택할 수 있어, 캐시를 더욱 효율적으로 관리하고 자원의 낭비를 줄일 수 있다. 예를 들어, TTL(Time to Live)을 설정하여 일정 시간 후에 자동으로 캐시를 갱신하거나, LRU(Least Recently Used) 정책을 적용해 자주 사용되지 않는 데이터를 자동으로 삭제할 수 있다.  

## 캐시의 종류
### 캐시 메모리(Cache Memory)
캐시 메모리는 레지스터, 메인 메모리와 함께 메모리 계층 구조의 전통적인 핵심 계층 중 하나로서, CPU의 처리 속도와 주 기억 장치의 접근 속도 차이를 줄이기 위해 사용한다.  
캐시 메모리는 참조 지역성(locality of reference)이란 동일, 인접한 항목이 다음에 더 자주 접근될 가능성이 높다는 원리를 기반하여 접근 속도 차이를 줄이게 된다.  
동작 과정은 다음과 같다.  
![Image](https://github.com/user-attachments/assets/44bb694c-7338-47e1-be0f-ca87c3143070)  
- [출처:https://www.geeksforgeeks.org/cache-memory-in-computer-organization](https://www.geeksforgeeks.org/cache-memory-in-computer-organization)

CPU가 데이터를 필요로 할 때, 먼저 1차적으로 캐시에서 확인하게 된다. 이때, 캐시에 존재한다면 Cache Hit가 발생하게 되어, CPU가 데이터를 캐시에서 빠르게 읽어올 수 있다.  
만약 그렇지 않다면 Cache Miss가 발생되어, 캐시는 새 항목을 할당하여 주기억장치에서 데이터를 가져와 캐시에서 요청을 처리한다.  

### 디스크 캐시(Disk Cache)
디스크 캐시 또는 버퍼 캐시라고 하며, 최근에 접근한 데이터를 메모리에 임시로 저장하여 디스크 입출력(I/O) 성능을 개선하는 메커니즘이다.  
보조 기억 장치는 일반적으로 램보다 느리기 때문에 캐시를 사용함으로써 속도 향상, 디스크 부하 감소, 성능 최적화를 할 수 있다.  
때문에, 디스크 캐시의 목적은 디스크의 성능을 최적화하는 것이다.  
![Image](https://github.com/user-attachments/assets/3f7d8cbe-91d4-4225-978f-7b45dd193a08)  
- [출처:https://www.geeksforgeeks.org/types-of-cache/#2-disk-cache](https://www.geeksforgeeks.org/types-of-cache/#2-disk-cache)

1. **데이터 요청**  
    디스크에 저장된 데이터를 처음으로 읽을 때, 해당 데이터는 디스크 캐시에 저장된다.
2. **빠른 접근**  
    이후 동일한 데이터를 요청하면, 디스크 캐시에서 바로 데이터를 제공하여 디스크로부터 직접 읽는 것보다 훨씬 빠르게 데이터를 반환한다.
3. **캐시 교체**  
    디스크 캐시가 일정 용량을 초과하면, 오래된 데이터는 새로 들어온 데이터와 교체된다. 이 과정은 운영 체제의 관리 하에 자동으로 이루어진다.

### 브라우저 캐시(HTTP Cache)
웹 브라우저 캐시는 사용자가 HTTP 요청 시, 자주 사용되는 리소스를 캐시에 저장하여, 다음 방문 시 빠르게 로드할 수 있도록 하는 캐시이다.  
이를, HTTP Cache 또는 단일 사용자의 정보만 저장하는 사설 캐시(Private Cache)라고 한다.  
그러면 어떻게 저장하고 가져오는 것일까?  
![Image](https://github.com/user-attachments/assets/145d5ba5-4569-4a8d-adbb-68b50db3f779)  
- [출처:https://pressidium.com/blog/browser-cache-work](https://pressidium.com/blog/browser-cache-work)

브라우저가 웹 서버에 콘텐츠를 요청 시, 만약 그 콘텐츠가 브라우저 캐시에 없다면 웹 서버에서 직접 가져온다. 반면, 콘텐츠가 이전에 캐시되어 있다면 서버를 우회하고 브라우저 캐시에서 직접 콘텐츠를 불러오게 된다. 이때, 캐싱 처리 여부 기준과 저장은 여러 가지 방침에 의거하여 결정되는데 이를, 캐싱 정책이라고 한다.  
이 정책은 일반적으로 HTTP/1.1에서 도입된 HTTP 헤더 Cache-Control을 사용해서 설정하게 된다. Cache-Control은 브라우저가 어떻게 동작할지에 대한 여러 가지 값을 제공하고 있다. 몇 가지를 소개하자면….
- **max-age, s-maxage** 
max-age는 브라우저 캐시에서 엔티티 유효 시간을 초 단위로 정의하는 옵션이고 s-maxage는 같은 개념이지만 중간 프록시 캐시에서 동작한다.  
- **no-cache**  
캐싱된 콘텐츠를 사용하려면 서버에게 사용 여부를 검증받아야 한다.  
- **no-store**  
반환된 엔티티를 브라우저가 캐싱하지 않는다. 즉, 캐싱 처리를 금지하는 옵션이다. 민감한 데이터나 자주 변경되는 데이터에 주로 사용된다.  
- **public, private**
public은 캐싱이 가능을 의미하며, 브라우저와 중간 프록시에서도 캐시가 가능하다. 그리고, 여기서 private 키워드는 위에서 언급한 사설 캐시라고 한다. 엔티티가 사설임을 알려, 브라우저에서만 캐시되고, 중간 프록시에서는 캐시가 동작하지 않게 한다.  
<br>

### 웹 프록시 캐시(Web Proxy Cache)
웹 프록시 캐싱은 웹 콘텐츠의 복사본을 사용자 가까이에 저장하여 여러 사용자가 동일한 콘텐츠를 요청할 때 원래 서버에서 콘텐츠를 가져오는 대신, 캐시에서 바로 제공하는 메커니즘이다.  
그렇다면 캐시는 어떻게 동작할까? 구조와 같이 알아보자.  

<img src="https://github.com/user-attachments/assets/a525cd17-7f5e-40a5-ac2d-eedcb38e31dd" style="width: 60%; height: auto;">  
- [출처:https://www.geeksforgeeks.org/web-proxy-caching-in-distributed-system](https://www.geeksforgeeks.org/web-proxy-caching-in-distributed-system)

1. **클라이언트 요청**
    클라이언트는 특정 웹 콘텐츠를 요청하기 위해 웹 프록시에게 HTTP GET 요청을 보낸다.  
2. **로컬 캐시 확인**
    웹 프록시는 먼저 자신의 로컬 캐시에서 요청된 콘텐츠를 찾는다.  
3. **캐시 히트(Cache Hit)와 캐시 미스(Cache Miss)**
    콘텐츠가 로컬 캐시에서 발견된다면, 이를 캐시 히트라고 하며 프록시는 그 콘텐츠를 클라이언트에게 바로 전달하여 요청을 빠르게 완료한다. 그러나, 콘텐츠가 로컬 캐시에 없으면, 프록시는 다음 단계가 진행된다.  
4. **이웃 프록시 캐시 조회(Query Neighboring Proxy Caches)**
    로컬 캐시에 콘텐츠가 없을 경우, 웹 프록시는 네트워크 내 다른 프록시 서버들에 해당 콘텐츠가 있는지 문의한다. 이 단계는 프록시 캐시가 분산되어 있는 특성을 활용해 클라이언트와 더 가까운 곳에서 콘텐츠를 찾을 확률을 높이며, 원래 웹 서버에 대한 부하를 줄이고 대기 시간을 감소시킨다.  
5. **웹 서버로 요청 전달(Forward Request to Web Server)**
    이웃 프록시 캐시에서도 콘텐츠를 찾을 수 없으면, 웹 프록시는 요청을 원래의 웹 서버로 전달한다. 웹 서버는 요청을 처리하고 콘텐츠를 웹 프록시로 반환한다.  
6. **콘텐츠 캐싱(Caching the Content)**
    웹 프록시는 웹 서버에서 받은 콘텐츠를 자신의 로컬 캐시에 저장하여, 향후 동일한 콘텐츠 요청이 있을 때 바로 로컬 캐시에서 제공할 수 있도록 한다. 이 단계는 성능을 향상시키고 네트워크 트래픽을 줄이는 데 도움을 준다.  
7. **클라이언트에게 콘텐츠 전달(Delivering Content to Client)**
    마지막으로, 웹 프록시는 콘텐츠를 클라이언트에게 전달하여 요청을 완료한다.  

웹 프록시 서버는 다양한 캐싱 방식을 사용해서 성능 최적화를 이루어낸다.
1. **캐시 계층 구조(Cache Hierarchies)**  
   계층형 캐싱을 활용해, 로컬 캐시에서 콘텐츠를 찾지 못했을 때 부모 캐시로 요청을 전달합니다. 이를 통해 더욱 빠르게 콘텐츠를 찾을 수 있다.  
2. **캐시 교체 정책(Cache Replacement Policies)**
    - **최소 최근 사용 알고리즘(LRU)** → 최근에 사용하지 않은 데이터를 우선적으로 제거  
    - **최소 빈도 사용 (LFU) →** 사용 빈도가 낮은 데이터를 우선적으로 제거  
    - **TTL (Time-to-Live) →** 콘텐츠의 유효 기간을 설정하여 일정 시간이 지나면 캐시에서 자동으로 제거  
3. **부하 분산(Load Balancing)**
여러 프록시 서버에 요청을 균등하게 분배하여 단일 서버에 부하가 과중되지 않도록 한다. 대표적 부하 분산 알고리즘에는 라운드 로빈(Round-Robin)이 있다.  
1. **압축(Compression)**
    캐시된 콘텐츠를 압축하여 저장 공간을 절약하고 데이터 전송 속도를 향상시킨다. HTTP 압축 기법인 Gzip 또는 Brotli와 같은 기법을 사용하여 웹 콘텐츠 크기를 줄인다.  
2. **프리패칭(Prefetching)**
    사용자 행동과 접속 패턴을 분석하여 미리 예측된 콘텐츠를 캐싱, 예를 들어, 
    인기 있는 콘텐츠를 식별 및 비혼잡 시간대에 미리 캐시하여 사용자 요청 시 빠르게 제공  
3. **콘텐츠 배급 네트워크(CDN)**
    CDN과 통합하여 캐시된 콘텐츠를 전 세계적으로 분배함으로써 사용자에게 가장 가까운 엣지 서버에서 콘텐츠를 제공해 지연 시간을 줄일 수 있다.

### DNS 캐시(DNS Cache)
DNS 캐싱은 DNS 조회 결과를 디바이스나 네트워크 내에 임시로 저장하는 과정이다.  
웹사이트를 방문할 때마다 도메인 이름 시스템(DNS)은 도메인 이름을 IP 주소로 변환하는 작업을 수행하는데, DNS 캐시가 없으면 이 과정은 매번 반복되어 불필요한 지연이 발생하게 된다.  

### 분산 캐시(Distributed Cache)
![Image](https://github.com/user-attachments/assets/43853369-287c-451a-979a-9b418691906c)  
- [출처:https://hazelcast.com/foundations/caching/distributed-cache](https://hazelcast.com/foundations/caching/distributed-cache)

분산 캐시는 기존 로컬의 캐시 메모리를 확장하여, 이를 여러 서버에 걸쳐 데이터를 분산 저장하여 캐싱을 효율적으로 관리하는 분산 아키텍처 또는 분산 클러스터이다.  

**분산 캐시는 어떻게 캐시 메모리를 확장할 수 있었을까?**  
여러 네트워크에 연결된 호스트들의 접근 가능한 램을 하나의 인 메모리 데이터 저장소로 통합했기 때문이다. 때문에, 기존 로컬 램 성능의 한계를 극복 및 시스템의 확장성과 성능을 높인다. 이러한 개념을 분산 아키텍처 혹은 분산 클러스터라고 한다.  

분산 캐시는 높은 확장성과 고용량 데이터 처리에 최적화되어 있다. 왜냐하면, 필요에 따라 클러스터에 더 많은 호스트 램을 추가함으로써, 점진적인 확장 스케일링(scaling)이 가능하기 때문이다. 따라서 데이터가 늘어남에 따라 캐시도 함께 확장이 가능한 구조다. 그리고 이러한 구조 특색으로 대규모 웹 애플리케이션이나 클라우드 환경에서 매우 적합하다. 왜냐하면, 분산된 서버들이 각각의 역할인 데이터를 처리하고 캐싱 처리하기 때문이다. 그래서 단일 서버의 성능 한계를 극복하고, 대규모 데이터를 효율적으로 관리하고, 빠른 응답 속도를 제공한다. 뿐만 아니라, 데이터를 네트워크의 여러 위치에 캐시해두면 네트워크 트래픽을 줄이고, 다른 애플리케이션들이 사용할 수 있는 대역폭을 확보할 수 있다.  

분산 캐시의 특징들을 정리하면 다음과 같은 장점으로 요약될 수 있다.  
1. **데이터 접근 속도 향상**
    여러 서버의 메모리를 하나의 데이터 저장소처럼 사용하여 데이터 접근 속도를 크게 향상시킬 수 있다.  
2. **확장성**
    시스템의 요구사항이 커질 때, 클러스터에 추가 컴퓨터를 더하여 처리 용량과 캐시 용량을 늘릴 수 있다.  
3. **부하 분산**
    여러 서버에서 데이터를 분산 처리하여 특정 서버에 부하가 집중되지 않도록 하여 시스템 안정성을 높일 수 있다.  
4. **네트워크 비용 절감**
    네트워크 요청 대신 메모리에서 직접 데이터를 읽어들이므로 네트워크 트래픽이 감소하고 다른 애플리케이션에 더 많은 대역폭을 할당할 수 있다.  
5. **하드웨어 비용 절감**
    하드웨어 업그레이드 없이도 애플리케이션 확장을 가능하게 하여, 더 저렴한 방법으로 애플리케이션을 확장 가능하다.  
6. **고가용성**
    데이터를 여러 노드에 복제하여 서버 장애가 발생해도 데이터를 계속 사용할 수 있다.  
<br>

지금까지 전반적인 분산 캐시에 대해 살펴보았다. 이제 분산 캐시 구조를 채택한 다양한 종류와 실제 활용 사례에 대해 알아보자.  
분산 캐시 솔루션 종류는 대표적으로 Redis, Memcached, Hazelcast, Apache Ignite 등이 있다.  
분산 캐시는 다양한 분야에서 활용될 수 있다. 예시로, 전자 상거래 웹사이트나 소셜 네트워크 서비스 그리고 온라인 스트리밍 플랫폼에서 중요한 역할을 한다.  
1. 전자상거래 웹사이트에서는 상품 정보를 캐시에 저장하여, 빠르게 조회할 수 있다.  
2. 소셜 네트워크 서비스에서는 사용자 프로필 정보를 캐시에 저장하여, 빠른 응답 속도를 제공한다.  
3. 온라인 스트리밍 플랫폼에서는 영상 메타데이터와 자주 조회될 콘콘텐츠를 캐시 서버에 저장하여, 더 빠른 스트리밍 속도와 효율적인 트래픽 처리가 가능하다.  
<br>

**분산 캐시는 로컬 캐시 방식의 데이터 정합성 문제 이슈를 해결할 수 있는 구조다.**

- [출처:https://tech.kakaopay.com/post/local-caching-in-distributed-systems](https://tech.kakaopay.com/post/local-caching-in-distributed-systems)

기존 로컬 캐시 구조는 서버 간 데이터 공유가 불가능하기 때문에 캐싱된 데이터에 따라 서버 간 데이터 불일치 문제가 발생하게 된다. 그러나 캐시 솔루션 방식을 사용해서 스케일 아웃(Scale-Out)을 한다면 위의 그림처럼 서버 간 데이터 공유가 가능하게 된다.  

이처럼 다양한 분야에서 분산 캐시를 활용하는 이유는, 자주 사용되는 데이터를 캐시에 저장함으로써 데이터베이스나 원격 서버에 대한 접근을 최소화하고, 응답 시간을 단축시키며 시스템 부하를 줄일 수 있기 때문이다. 이를 통해 더욱 빠르고 효율적인 서비스 제공이 가능하다.
