# 소개
서버가 클라이언트의 인증을 확인하는 방식에는 쿠키, 세션, 토큰 등이 대표적으로 사용된다. 이들 기술이 필요한 이유를 먼저 살펴본 후, 각각의 개념과 특징에 대해 자세히 알아보자.

## 왜 인증이 필요한가?
서버가 인증을 요구하는 이유는 **보안, 자원 보호, 무단 접근 방지, 서비스 제공, 신뢰성**을 보장하기 위함이다. 
인증을 통해 서버는 클라이언트와의 상호작용을 안전하고 효율적으로 관리할 수 있다. 
1. **사용자 식별**
서버는 클라이언트를 식별하여 적절한 데이터와 서비스를 제공한다. 예를 들어, 사용자 A의 요청에는 사용자 A에 맞는 정보와 응답이 제공되어야 한다.
2. **무단 접근 방지**
인증을 통해 서버는 요청이 적합한 사용자나 시스템으로부터 온 것인지를 확인할 수 있다. 이를 통해 자원 탈취나 악의적 공격으로 인한 데이터 손상 또는 유출을 방지한다.
3. **상태 유지/추적**
인증된 클라이언트는 로그인 상태를 유지하며, 사용자 맞춤형 서비스나 정보를 지속적으로 제공받을 수 있다.

## Cookie
쿠키는 브라우저에 저장되는 Key-Value 형식의 데이터로, 개인화 설정에 쓰이거나 혹은 인증 방식 중 하나로 쓰인다. 각 클라이언트마다 고유한 쿠키를 보유하고 있어 정보 식별과 상태 정보를 저장하는 데 유용하다. 그러나 쿠키에는 몇 가지 단점이 있다.  
* **보안 위험**: 쿠키가 XSS(Cross-Site Scripting) 공격과 같은 행위에 유출되거나 조작될 위험이 존재한다.
* **용량 제한**: 쿠키의 크기에 제한이 있어 저장할 수 있는 정보량이 한정적이다.
* **호환성 문제**: 브라우저에 따라 호환되지 않는 쿠키 종류가 있을 수 있다.
* **네트워크 부하**: 쿠키 크기가 커지면 네트워크 부하가 증가할 수 있다.  

### 인증 방식
1. 클라이언트는 서버에 요청을 보낸다.
2. 서버는 응답 헤더에 Set-Cookie 인증 정보를 담아 보낸다.
3. 이후 요청 때마다, 요청 헤더에 쿠키를 담아 클라이언트를 식별한다.

## Session
세션은 쿠키의 보안적 단점을 보완하기 위해 인증 정보나 상태 데이터를 서버 측에 저장하고 관리하는 방식이다. 서버는 클라이언트의 상태를 추적하는 정보를 서버 메모리 또는 데이터베이스에 저장하여 관리한다. 이 방식은 클라이언트 측에서 중요한 정보가 유출될 위험을 줄이고, 보안성을 높일 수 있어, 상태를 관리하는 Stateful 특성을 가진다.  

세션은 클라이언트가 서버와 상호작용할 때마다 고유한 세션 ID를 쿠키로 클라이언트에 전달하고, 서버는 이를 사용하여 세션 데이터를 조회하고 상태를 유지한다. 세션 ID는 외부에 노출되더라도 민감한 데이터를 포함하지 않기 때문에 본래 안전하지만, 해커가 세션 ID를 탈취해서 위장할 수 있는 위험성이 있다. 또한, 클라이언트의 요청 수가 많아짐에 따라 각 서버 간의 세션 정보 공유 및 관리가 복잡해지고, 이로 인해 서버 확장성에 어려움이 발생할 수 있다.  

### 인증 방식
![Image](https://github.com/user-attachments/assets/f5dd8983-55f3-4715-8e2a-3955dcdd80da)  
[출처: [JWT] 토큰(Token) 기반 인증에 대한 소개](https://velopert.com/2350)  

1. 사용자 로그인 요청에 대한 Session을 서버에 저장 후, 식별 목적의 Session Id를 쿠키에 전달한다.
2. 이후 요청마다 클라이언트는 해당 서버에 Session Id를 쿠키에 담아 전송한다.
3. 서버는 받은 Session Id와 서버에 저장된 Session과 비교하여 인증을 수행한다.

## Token
토큰은 서버가 클라이언트에게 제공하는 암호화된 인증 표식(문자열)이다. 보안성을 높이기 위해 HTTPS 프로토콜을 통해 전송되며, 중간에 유출될 가능성이 적다. 토큰은 서버에서만 해독 가능하므로 보안성이 높다. 또한 서버는 상태를 가지지 않는 Stateless 특성 덕분에 요청이 많을 때 서버를 분산할 필요가 없다.

하지만 토큰의 데이터 길이가 길어지면 인증 과정에서 오버헤드가 발생할 수 있고, 토큰의 Payload는 암호화되지 않아서 민감한 정보를 포함해서는 안 된다. 토큰이 유실되거나 탈취되면 문제가 될 수 있지만, 토큰에 만료 시간을 설정하여 무효화 처리가 가능하다. 그러나 유효한 토큰이 탈취되면 그 즉시 대처하기 어렵다. 그래서 이를 방지하기 위한 방법이 JWT의 Refresh Token과 Access Token의 역할 분담이다. JWT는 이후에 다룰 예정이다.

토큰은 모바일 앱이나 SPA(Single Page Application)에서 주로 사용되며, 프로토콜에서는 OAuth 2.0이 토큰 기반 인증 방식을 채택하고 있다.

### 인증 방식
![Image](https://github.com/user-attachments/assets/f91bfa9e-ab7e-4716-9f01-b8c35feb82dc)  
[출처: [JWT] 토큰(Token) 기반 인증에 대한 소개](https://velopert.com/2350)  

1. 로그인을 할 경우, 서버 측에서 고유 토큰을 생성 후에 클라이언트에게 응답 값으로 전달한다.
2. 클라이언트는 토큰을 쿠키나 스토리지에 저장해 두고, 서버에 요청을 할 때마다 해당 토큰을 Http 요청 헤더에 포함시켜 전달한다.
3. 서버는 전달 받은 토큰을 검증한다. 토큰 내부에 데이터가 포함되어 있어, 따로 조회할 필요는 없다.
