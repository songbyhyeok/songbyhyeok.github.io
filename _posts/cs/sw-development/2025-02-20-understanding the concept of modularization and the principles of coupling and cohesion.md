# 소개
초기의 소프트웨어나 시스템 개발은 점차 복잡해짐에 따라 여러 문제에 직면하게 되었다.
1. **시스템의 복잡성 증가**  
프로그램이 커지고 복잡해짐에 따라, 전체 코드를 관리하기 어려웠다.  
2. **유지보수와 확장성 문제**  
초기 시스템에서는 한 번 작성된 코드나 프로그램을 수정하거나 확장하는 데 많은 시간이 걸리고, 기존의 코드가 변경되면 다른 부분에 예상치 못한 영향을 미치는 일이 많았다.  
3. **코드 재사용성 부족**  
초기에 소프트웨어는 기능을 구현하는 데 반복적인 노력이 필요했다.
4. **협업의 어려움**  
대규모 프로젝트에서 여러 개발자가 동시에 작업할 때, 모든 사람이 같은 코드베이스에서 작업하면 충돌이나 혼란이 발생하기 쉬웠다.
5. **디버깅과 문제 해결의 어려움**  
전체 프로그램을 한 번에 테스트하고 디버깅해야 했기 때문에, 프로그램이 커질수록 모든 부분을 동시에 테스트하고 문제를 찾는 것이 매우 어려웠다.  
<br>

모듈화는 이러한 문제들을 해결하고 효율성을 높이기 위해 도입되었다.

## 모듈화란(Modularization)?
모듈화란 소프트웨어를 각 기능별로 나누는 과정을 말합니다. 각 기능을 독립적인 모듈로 나누어, 이를 관리하고 수정하는 데 용이하도록 만드는 것이다. 이때 모듈은 서브루틴, 프로그램, 작업 단위 등으로 불리며, 각 모듈은 특정한 기능을 독립적으로 수행한다. 이러한 나눔은 시스템을 효율적이고 유지보수하기 쉽게 만든다.  

## 모듈화 예시
모듈화된 시스템은 각 모듈을 개별적으로 개발하거나 수정할 수 있어 효율적이며, 문제가 발생했을 때 해당 모듈만 수정하면 되어 시스템 전반에 미치는 영향을 최소화할 수 있다.  

모듈화는 프로그래밍에만 국한되지 않으며, 현실 세계의 다양한 분야에서도 부분적으로 모듈화를 통해 효율적으로 작업을 처리한다.

그렇다면 좋은 모듈화와 나쁜 모듈화는 어떤 기준으로 구분할 수 있을까?  

## 좋은 모듈화와 나쁜 모듈화
### 좋은 모듈화
좋은 모듈화는 독립성이 높은 모듈로 나누는 것이다. 각 모듈이 주어진 기능만을 독립적으로 수행하고, 다른 모듈과의 상호 의존성이 적어야 한다. 이렇게 하면 모듈을 수정하더라도 다른 모듈에 미치는 영향이 최소화되며, 오류가 발생하더라도 문제를 쉽게 추적하고 해결할 수 있다.  

좋은 모듈화는 다음과 같은 조건을 만족한다.  
- **높은 응집도(Cohesion)** 
  - 하나의 모듈 내에서 관련된 작업들만 수행되므로, 모듈이 잘 정의된 책임을 가지고 독립적으로 동작한다.
- **낮은 결합도(Coupling)**
  - 다른 모듈에 의존하지 않거나 최소한의 의존만 가진다. 이렇게 하면 수정이 용이하고, 각 모듈을 독립적으로 테스트할 수 있다.  
<br>

**구체적 예시**  
예를 들어, 사용자 관리 모듈과 결제 처리 모듈이 있다고 할 때, 각 모듈은 자신이 담당하는 기능만을 수행한다. 사용자 관리 모듈은 사용자를 등록하고 정보를 관리하는 데 집중하며, 결제 처리 모듈은 결제를 처리하는 데만 집중한다. 두 모듈은 서로 독립적으로 동작하며, 변경이 필요할 때 다른 모듈에 영향을 주지 않는다.  
<br>

### 나쁜 모듈화
나쁜 모듈화는 독립성이 낮은 모듈로 나누어진 경우이다. 응집도가 낮고 결합도가 높은 모듈들은 서로 의존성이 많아, 하나의 모듈을 수정하면 다른 모듈에 큰 영향을 미치게 되기 때문에, 유지보수와 확장성에 어려움을 겪게 된다.  

나쁜 모듈화는 다음과 같은 조건을 만족한다.  
- **낮은 응집도**
  - 모듈이 여러 가지 책임을 지고, 서로 관련 없는 작업들을 함께 처리하게 되어 모듈의 목적이 분명하지 않다.
- **높은 결합도**
  - 모듈들이 서로 많이 의존하여, 한 모듈의 변경이 다른 모듈에 큰 영향을 미치게 된다.  
<br>

**구체적 예시**  
사용자 관리 모듈과 결제 처리 모듈이 하나의 모듈에 함께 구현된 경우, 두 기능은 독립적으로 수행되기보다는 서로 얽혀서 처리된다. 이 경우 하나의 기능을 수정할 때 다른 기능에 영향을 미치며, 오류를 찾고 수정하는 데 어려움이 따른다.  
<br>

## 모듈화의 측정 방법
![Image](https://github.com/user-attachments/assets/ec9cae13-a4a9-45ad-8a46-06d9161bb6a5)  
[출처:https://stackoverflow.com/questions/14000762/what-does-low-in-coupling-and-high-in-cohesion-mean](https://stackoverflow.com/questions/14000762/what-does-low-in-coupling-and-high-in-cohesion-mean)  

모듈화의 품질을 평가하려면 **결합도(Coupling)**와 **응집도(Cohesion)**를 측정하는 것이 중요하다. 이 두 가지 특성은 모듈의 독립성을 결정하는 핵심 요소이기 때문이다.  

### 응집도(Cohesion)
응집도는 하나의 모듈 내에서 관련된 작업들이 얼마나 잘 결합되어 있는지를 나타낸다. 높은 응집도를 가진 모듈은 단일 책임을 가지며, 특정 기능만 수행한다. 즉, 응집도가 높을수록 모듈 내의 요소들이 서로 강하게 연결되어 하나의 목적을 잘 수행하게 되는 것이다.  

**응집도의 예시**  
- **높은 응집도**
    - 하나의 모듈이 오직 사용자 등록 기능만을 담당하고, 관련된 모든 기능(이메일 확인, 비밀번호 검증 등)을 처리한다면, 이 모듈은 높은 응집도를 가진다.  
- **낮은 응집도**  
  - 하나의 모듈이 사용자 등록뿐만 아니라 결제 처리, 로그인 처리 등의 여러 다른 작업도 함께 수행한다면, 이는 응집도가 낮은 모듈이다. 여러 책임을 처리하기 때문에 유지보수가 어렵고, 모듈 간의 의존성이 커질 수 있다.  
<br>

### 결합도(Coupling)  
결합도는 모듈 간의 의존성 정도를 나타낸다. 결합도가 낮을수록 모듈들은 서로 독립적이고, 변경이나 수정 시 다른 모듈에 미치는 영향이 적다. 반대로 결합도가 높으면, 한 모듈의 수정이 다른 모듈에 큰 영향을 미친다.  

**결합도의 예시:**  
- **낮은 결합도**
  - 사용자 관리 모듈과 결제 처리 모듈이 서로 독립적이고, 각 모듈은 인터페이스나 간단한 데이터 전달을 통해 최소한의 의존성만 가질 때, 결합도는 낮다.  
- **높은 결합도**
  - 두 모듈이 서로의 내부 구현에 깊게 의존하거나, 하나의 모듈이 다른 모듈의 데이터 구조를 직접 변경하거나 참조하는 경우, 결합도가 높다. 이럴 경우 하나의 모듈 수정이 다른 모듈에 영향을 미치게 된다.
