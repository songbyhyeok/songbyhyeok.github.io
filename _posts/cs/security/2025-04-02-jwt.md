# JWT(JSON Web Token)
인증(Authentication)에 필요 정보들을 JSON 객체 형태로 만든 토큰을 말한다.  

사용자가 인증 요청 시 서버가 JSON 토큰을 발급한다. JSON 토큰에는 사용자의 정보를 담고 있어서 브라우저가 요청 때마다 서버는 JSON 토큰의 변조 여부를 확인 후에 인증을 처리한다. 변조 됐는지 확인할 수 있는 이유는 헤더와 페이로드를 기반으로 생성되기 때문에, 내용이 변조되지 않았음을 확인 가능하기 때문이다. 그리고 JWT에 사용자 권한이나 역할 정보 등을 담아 서버에서 요청을 처리할 때 사용자에게 적합한 권한을 부여할 수도 있다.  

JSON 토큰은 변조를 방지하기 위해 암호화 처리를 하게 되는데, 이때 사용되는 암호화 방식은 양방향 암호화 방식이고, 사용되는 서버 환경에 따라 대칭 혹은 비대칭 전략을 사용하게 된다.  

JWT는 클라이언트 측에서 토큰을 관리하기 때문에 무상태(Stateless)을 가진다. 그리고 사용자와 서버간에 상태를 공유할 필요 없이 인증을 처리할 수 있기 때문에 서버는 확장이 가능하여 분산 시스템 환경에서 유용하다.  

하지만, 설명만 들었을 땐 완벽할 수 있다고 생각할 수 있으나 JWT를 사용할 때는 서명된 토큰이 클라이언트에 저장되므로, 민감한 정보를 포함하지 않도록 해야 한다. 왜냐하면 구성의 일부는 base64로 인코딩 변환만 되어 있어 쉽게 내부 정보를 확인할 수 있기 때문이다. 또한, 많은 데이터를 넣어 크게 만들어서도 안된다. 최종 토큰 단계에서 헤더의 크기가 8KB를 넘는 경우 이를 처리하지 못할 수 있기 때문이다. 아니면, 검증 과정에서 시간이 오래 걸리기 때문이다. 그리고 JWT 토큰은 중간에 탈취나 CSRF, XSS 공격에 취약하므로 토큰의 유효 기간을 최대한 짧게 설정하는 것이 좋다.  

JWT는 일반적으로 Single Sign-On(SSO)에서 많이 사용된다. SSO란? 1회 사용자 인증으로 다수의 애플리케이션 및 웹사이트에 대한 사용자 로그인을 허용하는 인증 솔루션을 말하는데, 즉 OAuth를 생각하면 된다. 하지만 나는 OAuth에 대해 아직 잘 모르므로 넘어가도록 하겠다.  

## 구조
```
xxxxx.yyyyy.zzzzz
```

JWT는 헤더(Header), 페이로드(Payload), 서명(Signature) 세 가지 요소로 구성되어 있다.  

### 헤더(Header)
```
{
  "algorithm": "HS256",
  "type": "JWT"
}
```

JWT의 타입과 사용하는 서명 알고리즘을 정의하는 곳이다.  

### 페이로드(Payload)
```
{
  "sub": "1234567890",
  "name": "John Doe",
  "iat": 1516239022
}
```

주로 사용자 정보나 권한, 토큰의 만료 시간 등을 저장한다. 이 곳의 정보는 암호화되지 않고 단순히 인코딩되기 때문에 민감한 정보는 저장하지 않는 것이 좋다.  

페이로드 구성엔 여러 개의 클레임을 포함하고 있다.  
등록된 클레임(Registered Claims, 공개 클레임(Public Claims), 개인 클레임(Private Claims) 이렇게 세 가지가 있는데, 사용하는 데, 크게 지장이 없으므로 더 분석하진 않을려고 한다. 그리고! 여기서 클레임이란 엔티티(사용자)에 정보라고 생각하면 좋다.  

### 서명(Signature)
```
HMACSHA256(
  base64UrlEncode(header) + "." +
  base64UrlEncode(payload),
  secret)
```

토큰의 무결성(변조 여부)을 보장하기 위해 헤더와 페이로드를 서명한 부분을 말한다. 여기서 이 서명을 생성하기 위해서는 비밀 키와 헤더에 정의된 알고리즘을 사용한다.  

서명 확인은 디코딩된 헤더와 페이로드로 새로운 서명을 생성한 후, 원래 토큰에 포함된 서명과 비교하여 유효성을 확인한다.  

## JWT 토큰을 전송할 때 어떻게 보내야 하는가?
### Authorization: Bearer
```
Authorization: Bearer <token>
```
반드시는 아니지만 사용자가 보호된 경로나 자원에 접근하고자 할 때, Authorization의 인증 방식 중 하나인 Bearer 스키마를 사용하여 전송하는 것이 좋다. 이 헤더는 유효한 JWT인지 확인 후에, 유효하다면 사용자는 보호된 자원에 접근할 수 있게 된다.  

## JWT 검증(Validation)과 확인(Verification) 과정
### JWT 검증
토큰이 올바른 형식을 갖추었고 예상된 데이터가 포함되었는지 확인하는 작업이다.  
1. 구조: 토큰이 표준적인 세 부분(헤더, 페이로드, 서명)을 가졌는지 확인
2. 형식: 헤더와 페이로드가 Base64URL로 인코딩 되었는지?
3. 내용: 페이로드의 클레임이 유효한지 확인한다, 예를 들어 만료 시간(exp), 발급 시간(iat), 사용 시작 시간(nbf) 등이 올바른지를 본다.

### JWT 확인
토큰이 변조되지 않았는지? 그리고, 신뢰할 수 있는 발급자에게서 온 것인지 확인한다.  
1. 서명 확인: JWT의 서명이 헤더와 페이로드에 대해 정확하게 계산된 것과 일치하는지 확인
2. 발급자(iss) 확인: `iss` 클레임이 예상한 발급자와 일치하는지 확인
3. 대상(aud) 확인: `aud` 클레임이 예상된 대상과 일치하는지 확인

## Access Token과 Refresh Token
Access와 Refresh는 JWT (JSON Web Token) 기반 인증 시스템에서 사용되는 두 가지 주요 토큰을 말한다.  

### Access
사용자가 인증을 받고, 특정 자원에 접근할 수 있는 권한을 가진 인증 토큰을 말한다.  
1. 짧은 유효 기간: Access Token은 보통 짧은 유효 기간을 가지며, 사용자가 자원을 요청할 때마다 서버에 전송
2. 권한 부여: Access Token은 사용자의 권한 정보를 담고 있어, API 서버가 해당 사용자가 특정 자원에 접근할 수 있는지 확인하는 데 사용
3. 토큰 발급: 사용자가 로그인하면 서버는 사용자의 인증 정보를 기반으로 Access Token을 발급  

### Access Token 문제점
JWT 토큰은 사용자가 관리하는 stateless 특성을 가진다. 때문에 JWT 토큰을 탈취나 유출될 경우, 토큰 유효 기간이 남아있다면 속수무책으로 넋놓고 바라보고 있어야만 한다. 이에 대한 대응이 유효 기간을 매우 짧게 설정하는 건데, 근데 문제는 사용자 입장에서 번거롭게 로그인을 자주 해줘야 하는 상황이 발생한다는 점이다. 그래서 이에 대한 해결책이 바로 RefreshToken이다.  

### Refresh Token
Access Token의 유효 기간이 만료되었을 때 새로운 Access Token을 발급받기 위한 토큰을 말한다. 그래서 RefreshToken의 유효 기간은 최소 2주 정도로 길게 잡아둔다.  
1. 긴 유효 기간: Refresh Token은 일반적으로 Access Token보다 훨씬 긴 유효 기간을 가진다.
2. 새로운 Access Token 발급: 사용자가 로그인하고 Access Token이 만료된 후, Refresh Token을 사용해 새로운 Access Token을 발급받을 수 있다.
3. 서버측 저장: Refresh Token을 DB나 인메모리에 저장한다.  

### Refresh Token Rotation
리프레시 토큰이 유효하면 언제든지 새로운 엑세스 토큰을 발급받을 수 있기 때문에 보안 위험이 존재한다. 왜냐하면 악의적인 사용자가 Refresh Token을 탈취하면, 계속해서 Access Token을 발급받을 수 있기 때문이다. 때문에, 이를 방지하기 위해 나온 방법이 Refresh Token Rotation이다. 이 방법은 매번 Refresh Token을 사용하여 Access Token을 발급받을 때, 기존 Refresh Token을 지우고 새로운 Refresh Token을 발급하는 방식이다.

### Access / Refresh Token 재발급 원리
- AccessToken 유효, RefreshToken 유효
    - 정상 처리
- AccessToken 만료, RefreshToken 유효
    - refresh token을 검증하여 access token 재발급
- AccessToken 유효, RefreshToken 만료
    - access token을 검증하여 refresh token 재발급
- AccessToken 만료, RefreshToken 만료
    - 에러 발생 (재 로그인하여 둘다 새로 발급)
