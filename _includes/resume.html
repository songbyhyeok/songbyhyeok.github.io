  • Nginx을 활용한 무중단 배포 ~ link

    1. GitHub Actions CI/CD에서 배포 중 애플리케이션 프로세스를 종료하고 재시작하는 동안, 서비스가 일시적으로 중단되어 모든 요청이 끊기고 502 오류가 발생했습니다.

    2. 이로 인해 사용자들은 접속 실패, 세션 만료, 작업 중단 등으로 인해 서비스 이용에 큰 불편을 겪게 됩니다.

  • 문제 해결:

    1. 서비스 무중단 배포를 위해 Nginx를 도입하고, Blue-Green 배포 전략을 적용했습니다. 두 개의 배포 환경(예: blue, green)을 운영하면서, 새 버전은 비활성화된 환경에 배포한 후 Nginx 설정의 upstream을 통해 트래픽을 신규 환경으로 전환하였습니다.

    2. 이 과정은 Nginx 설정 파일을 동적으로 갱신하고 nginx -s reload 명령어로 반영하며, 트래픽 전환 중에도 기존 환경은 정상적으로 사용자 요청을 처리합니다.

  • 결과:

    배포 중에도 서비스는 502 오류나 접속 실패 없이 안정적으로 유지되었고, 사용자 요청도 정상 처리되었습니다. 이로써 사용자 경험과 서비스 신뢰도가 향상되었습니다.

  • 토큰 동시 사용 문제 해결 방안과, 그로 인한 JWT Stateful Issue ~ link

    1. 사용자가 refresh token을 사용해 access token을 갱신한 뒤, 이전 refresh token이 탈취된 경우 공격자가 그 이전 토큰으로 다시 요청할 수 있습니다.

    2. JWT 자체는 stateless이지만, rotation token은 이전 refresh token이 재사용되었는지 확인하기 위해 서버에 저장해야 합니다.

  • 문제 해결:

    1. Refresh Token Rotation으로 발생할 수 있는 토큰 재사용 및 세션 탈취 문제는 Redis 기반의 블랙리스트를 통해 해결했습니다.

    2. 서버 측에서 Refresh Token의 고유 식별자와 만료 정보를 Redis에 저장하고, 이를 기반으로 토큰의 사용 여부와 유효성을 실시간으로 검증하는 방식으로 문제를 방지했습니다.

  • 결과:

    그 결과, 동일한 토큰의 재사용(Replay Attack)을 효과적으로 차단하고 세션 보안을 강화할 수 있었으며, Redis 기반의 상태 관리를 통해 stateful 구조의 복잡도는 줄이면서도 JWT 시스템의 stateless 특성은 그대로 유지할 수 있었습니다.

  • Private RDS 접근 ~ link

    1. AWS VPC의 Public Subnet에 위치한 RDS 인스턴스를 보안 및 성능 개선을 위해 Private IP로 변경한 결과

    2. 클라이언트가 Private Subnet에 위치한 RDS에 접근할 수 없어 데이터베이스 연결 오류가 발생하였습니다.

  • 문제 해결:

    1. 우회 접근 방법으로 SSM(Systems Manager)와 SSH 방식 중, 키 관리와 간단한 설정으로 터널을 생성할 수 있는 SSH 방식을 선택했습니다.

    2. SSH 터널을 통해 EC2 인스턴스를 중계점으로 설정한 후, VPC의 Private Subnet에 위치한 RDS에 접근하기 위해 로컬 포트 포워딩 방식을 사용하여 터널을 구축하였습니다.

  • 결과:

    로컬 환경에서 RDS 인스턴스로의 데이터베이스 연결이 성공적으로 이루어졌습니다.

  • 답글/대댓글 기능 구현 ~ link

    1. 답글/대댓글 기능 구현에는 크게 두 가지 방법이 있습니다. 1) 계층형 쿼리 처리, 2) 클라이언트에서 다진 트리 구조로 변환 후 DFS 방식

    2. 계층형 쿼리 방식은 데이터의 깊이가 깊거나 양이 많아질수록 다중 조인과 재귀 쿼리로 인해 성능 저하 및 DB 부하가 발생할 수 있습니다. 특히 트리 구조 데이터를 반복적으로 요청해야 하는 실시간 UI에서는 병목이 생기기 쉬웠습니다.

    3. 이러한 점을 고려하여, 데이터를 가져온 후에 클라이언트에서 다진 트리로 재구성한 후 DFS 방식으로 렌더링하는 방식을 채택했습니다.

    4. 이는 트리 구조와 DFS 방식에 익숙했고, 클라이언트에서 처리하는 편이 더 유연하고 확장성이 높다고 판단했기 때문입니다. 구현 과정에서 발생한 두 가지 주요 이슈와 그 해결 방법을 설명하겠습니다.

  • 1. 트리 구조 재정의

    1. 답글이나 대댓글을 처리하기 위해서는 하나의 부모가 여러 개의 자식을 가질 수 있는 구조가 필요하고, 각 데이터에는 메타데이터가 있어야 했습니다.

    2. 이에 따라 다진 트리 구조로 데이터를 재구성해야 했습니다.

  • 문제 해결:

    1. 데이터를 처리할 때, 먼저 레벨이 가장 낮은 부모들을 리스트에 저장하였습니다.

    2. 그 외의 자식들은 해당 부모의 자식 리스트에 저장하는 방식으로 해결했습니다.

  • 2. DFS 사용 방식에 따른 문제

    1. 레벨 0의 부모들을 게시판에 배치하는 과정에서, DFS 재귀 방식을 사용하면 등록일자 순으로 출력되는 문제가 발생했습니다.

    2. 이를 해결하기 위해 등록일자를 역순으로 처리하려 했으나, depth 0의 배치만 역으로 바뀌는 문제가 생겼습니다.

  • 문제 해결:

    DFS-스택 방식을 사용하여 자식들을 역순으로 먼저 삽입 이후에, 스택을 활용해 자식들을 먼저 처리한 후 부모를 출력하는 방식으로 문제를 해결했습니다.
